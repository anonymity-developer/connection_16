# 동료 탐색 전환 분석 MVP

`feat/admin-discovery-conversion`의 별도 작업이다. 최신 확인한 main `8b2d655`에서 시작하며, 열린 PR #37의 SYNC 질문 이벤트·V21에 의존하거나 해당 PR을 수정하지 않는다. main 병합·배포된 기능으로 해석하지 않는다.

관리자 화면은 `/admin/discovery-conversion`, 읽기 API는 `GET /api/v1/admin/discovery-conversion`이다. [OpenAPI](discovery-conversion.openapi.yaml)와 [집계 SQL](../backend/src/main/java/com/tagme/operations/DiscoveryConversionAnalytics.java)을 기준으로 한다.

## 데이터와 시간 순서

기존 V5 `sync_results`는 사용자당 현재 결과 한 행과 `submitted_at DATETIME(6)`을 가진다. V1 `profile_views`는 `(viewer_id,viewed_id)` PK, 본인 방문 금지 CHECK, `first_viewed_at DATETIME(6)`을 가진다. 프로필 열기 POST가 최초 행을 DB UTC 시각으로 저장하며 반복 방문 시각은 갱신하지 않는다. 별도의 상호 방문 플래그·형성 시각은 없다.

기준 사용자와 상대는 현재 ACTIVE·USER이고 자격증명 행이 있으며 `local_admin_accounts`에 없는 계정이다. 프로필 본문·이름·답안·개별 방문 원장을 반환하거나 추출하지 않는다. 현재 프로필의 작성 완성도·동의 버전은 과거 방문 기록의 추가 필터로 사용하지 않는다. 이 통계는 현재 탐색 가능한 사람 수와 다르다.

| 단계 | 실제 집계 기준 |
| --- | --- |
| SYNC ME 완료 | 기준 사용자와 조인한 현재 `sync_results` 수. 문항 버전 전체, 사용자당 1명. 수동 글자 지급만 있고 결과가 없으면 제외 |
| 완료 후 새 동료 프로필 방문 | 내 결과의 `submitted_at < profile_views.first_viewed_at`인 유효 상대가 하나 이상 있는 사용자 수. ‘새 동료’는 상대별 최초 방문이며 생애 첫 탐색을 뜻하지 않음 |
| 해당 동료와 상호 방문 형성 | 앞 단계의 **같은 상대**에 대해 역방향 행도 있고, `GREATEST(내 최초 방문, 상대 최초 방문) > 내 submitted_at`인 사용자 수 |

첫 시간 비교는 엄격한 `>`다. 제출과 방문이 같은 마이크로초면 선후를 증명할 수 없어 제외한다. 상대가 나를 먼저 방문한 뒤 내 완료 후 최초 방문으로 양방향이 되면 2·3단계가 동시에 성립한다. 내가 먼저 방문하고 상대가 나중에 방문해도 형성 시각은 두 시각 중 늦은 값이다. 단, 내 방문은 완료 이후여야 한다.

내가 완료 전에 봤던 A가 완료 후 나를 방문하고, 완료 후 처음 본 B와는 상호 방문이 아니라면 2단계만 센다. 서로 다른 상대의 근거를 합쳐 3단계를 만들지 않는다. 내 완료 전에 이미 양방향이었던 관계도 제외한다.

각 단계는 `COUNT(DISTINCT user_id)`로 사용자당 한 번 센다. 여러 상대와 상호 방문해도 한 사람이며, 같은 두 사람도 각자의 제출/방문 조건을 만족할 때 각 사용자로 한 번씩 집계된다. 관계 쌍의 개수가 아니다. 항상 `3단계 ≤ 2단계 ≤ 1단계`다.

직전 단계 전환율은 `현재 단계 / 직전 단계 × 100`, 완료 대비 전환율은 `현재 단계 / SYNC 완료 × 100`이다. 첫 행의 직전 전환율과 분모 0인 값은 null/—이며 실제 0%와 구분한다. 세 단계는 한 집계 SQL, 현재 관리자 권한/credential version 확인과 함께 REPEATABLE READ 트랜잭션으로 읽는다. 관리자 조회는 분당 30회, 트랜잭션 제한은 10초다.

## 초기화와 지원 조치

게임 초기화와 SYNC LOCK/REVOKE는 기존 서비스가 결과를 snapshot으로 보관하고 현재 `sync_results`에서 제거한다. 이 API는 snapshot JSON·과거 결과를 읽지 않는다. 다시 제출한 현재 결과만 새 기준 시각이 되며, 보존된 오래된 최초 방문은 그보다 앞서므로 전환으로 되살아나지 않는다.

다른 미션 조정도 generation을 올리지만 SYNC 결과를 유지할 수 있다. 따라서 모든 generation 변경 시각보다 제출이 늦어야 한다는 필터를 추가하지 않는다. 프로필 방문에는 generation 컬럼이 없으며, 관계는 게임 초기화로 초기화하지 않는다. 비활성화/새 가입은 기존 지원 정책에 따라 별도 user ID로 취급한다.

## 분석할 수 없는 것

- 추천 노출·추천 카드 클릭·실제 화면을 읽은 시간·실제 대화·친분·설문의 인과 효과를 측정하지 않는다. 저장된 프로필 열기 요청과 양방향 기록의 시간 관계만 보여준다.
- 완료 전에 방문한 상대의 완료 후 재방문은 원장에 새 시각이 없어 구분할 수 없다. 이 MVP의 상호 방문 수는 ‘완료 후 새 상대 방문’의 부분집합이며, 완료 전 상대에 대한 답방으로 새로 생긴 모든 상호 방문을 포함하는 지표는 아니다.
- 현재 남은 기록이면 화면 도입 전의 데이터도 집계할 수 있다. 삭제되거나 애초 기록되지 않은 과거 행동은 복원하지 않는다. 행의 최초 시각은 서버 DB 저장 시각이며 실제 클릭·네트워크 도착·커밋 시각을 따로 측정한 값이 아니다.
- 현재 상태가 바뀌면 사용자/상대가 집계에서 빠져 수치가 줄 수 있다. 고정된 과거 코호트 보고서가 아니며 비활성화 계정의 과거 총계도 아니다. 모든 문항 버전을 합산하므로 문항 버전 간 효과 비교로 해석하지 않는다.
- 새 행동 로그·DB 마이그레이션·추천 알고리즘 변경은 없다. 기존 PK·역방향 인덱스로 읽으며 실제 운영 규모의 부하 검증은 별도다. 재방문이나 추천 클릭 전환 분석이 필요해질 때에만 추가 기록의 목적·범위·보관 정책을 별도로 검토한다.

## 화면과 운영 경계

승인한 문구와 기존 관리자 틀·DM Sans를 유지한다. Achromatic ledger(시드 461493114)의 숫자 중심 표로 ‘SYNC 완료 후 몇 명이 새 상대 방문과 상호 방문으로 이어졌는가’를 답한다. 새 미션 퍼널·차트·개인 목록·다운로드·참가자 쓰기는 제공하지 않는다. 로딩·0·미정/분모 0·오류를 구분하고 새로고침을 제공한다. 숫자는 휴대폰에서도 오른쪽 정렬한다.

새 API는 기존 ADMIN 경로 보안과 같은 트랜잭션의 현재 DB 권한 검사를 사용한다. 비인증/일반 참가자는 거절하며 응답은 no-store 집계 DTO만 포함한다. 분석 조회 자체가 `sync_results`나 `profile_views`를 생성/갱신하지 않는다. 운영 서버/DB 접근·개인정보 추출·병합·배포는 이 작업에 포함하지 않는다. 새 DDL이 없어 추후 별도 승인된 배포/롤백은 서버·프론트 코드 버전만 전환하면 된다.
