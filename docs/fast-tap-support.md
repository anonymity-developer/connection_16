# FAST TAP 판정 복구·수집 순위·재도전

2026-11-17 확정 정책은 **기존 오판정 복구 → 인정 시각으로 전체 수집 순위 보정 → 복구할 기록이 없는 실패자만 재도전**이다. 공식 도전은 1회이며 무제한 최고 기록 경쟁으로 바꾸지 않는다.

## 신규 입력과 제출

- 정수 밀리초가 같은 입력을 허용한다. 브라우저 시간 정밀도·다중 터치만으로 전체 기록을 무효화하지 않는다.
- 5초 준비·10초 플레이, 입력 최대 1,000개·0~9,999ms·비감소 순서·소유권·현재 회차·태그 해금·중복 제출 검사는 유지한다. 화면 이탈/중단은 별도 처리한다.
- 새 도전의 제출 유예는 종료 후 60초다. 이미 발급한 도전의 원래 기한은 변경하지 않는다.
- 종료 전 제출은 거절한다. 동일 기록만 통신/서버 실패·시각 추정의 조기 제출 때 최대 3회 추가 전송하며 간격은 1/2/4초다. 회차 변경·인가 실패·요청 제한을 자동 재시도하지 않는다. 최초 응답이 저장 후 유실돼도 새 도전/중복 점수를 만들지 않는다.
- 응답 대기는 회당 8초로 제한한다. 유예가 남지 않으면 자동 재전송하지 않으며 수동 동일 요청은 이미 저장된 결과를 확인할 수 있다. 새로고침 후 탭 배열을 복원했다고 꾸미지 않는다.

## 원본 기록 복구

관리자 `/admin/tap-support`의 실패 목록에서 다음 조건을 만족하는 기록에만 **기존 기록 복구**를 제공한다.

1. 현재 슬롯의 보관되지 않은 원본 도전이며, 기존 동일 밀리초 INVALID·제출 지연 EXPIRED·레거시 REVIEW_REQUIRED다.
2. 서버 접수 시각·payload hash·입력 배열·횟수가 남아 있고 서로 일치한다. 무제출을 0회 제출로 간주하지 않는다.
3. 서버의 원래 10초 일정과 이벤트 범위를 충족하고 중단 이벤트가 없으며, 원래 종료 이상/종료+60초 이하에 접수됐다.
4. 현재 계정·프로필·참여 동의·태그 해금이 유효하고 이미 F를 획득하지 않았다. 원래 해금 전 수행과 행사 접수 기간 밖 기록은 복구하지 않는다.

복구는 실제 원본 기록을 VALID로 재분류하고 기존 점수와 서버 접수 시각으로 GAME_ATTEMPT 완료 근거를 만든다. 가상 점수나 ADMIN_ADJUSTMENT 지급으로 대체하지 않는다. 원래 입력·접수·기한은 덮어쓰지 않고 V21 `tap_recoveries`에 기존 판정/기한, 새 인정 기한, 원래 인정 시각, 운영자·사유·처리 시각·요청 키를 보관한다. 감사 실패 시 지급·복구 이력도 함께 롤백한다.

## 이미 다 모은 사람의 순위도 보정

현재 유효 완료자의 다섯 `accepted_received_at` 중 **최댓값**을 전체 수집 인정 시각으로 사용한다. 이를 오름차순 정렬하고 동점은 기존 내부 완료 번호·사용자 ID로 결정한다. 이미 다 모은 사람도 같은 비교에 포함되어 표시 순위가 바뀔 수 있다.

예: F가 11:00에 정상 접수됐고 나머지도 이전에 완료됐다면 전체 인정은 11:00이다. Y를 11:05에 마쳤다면 전체 인정은 11:05다. 복구 처리 시각을 11:00으로 위조하지 않는다. 원래 `event_completions.completion_order`와 처리 시각은 그대로 두고 조회 시 순위를 계산한다. 다섯 근거가 없는 레거시 완료 행만 기존 완료 시각으로 비교한다.

참가자 수집판·완성 안내·관리자 회원/완료 목록은 공통 순위 조회를 사용한다. 순위 변동만으로 획득 팝업을 다시 재생하지 않는다. 최종 시상 확정과는 구분하며 잠정 시상 근거는 복구 이력의 유효 기한을 함께 검증한다.

## 나머지 실패자 재도전

복구할 수 없는 무제출·기한 초과·중단·기존 실패 기록만 **재도전 허용** 대상이다. 원본 복구가 가능한 기록을 재도전으로 폐기하지 않도록 서버에서도 차단한다.

- 현재 실패 도전 ID와 expected generation을 확인하고 F 참여만 보관·초기화한다.
- **F 태그 해금, 계정·프로필·첫 S와 다른 미션은 유지**한다. 참가자는 새로고침 후 같은 게임에서 다시 시작한다.
- 정상 완료/진행 중 도전, 이미 F를 가진 사람은 이 실패 지원 API로 초기화하지 않는다.
- 이전 도전 입력과 변경 전 자료·운영 사유·감사를 보존한다. 오래된 요청이 새 회차를 되살리지 못하게 generation을 증가시킨다.

## 매크로 대응 경계

관리자에게만 동일 시각 입력 10쌍 이상, 30회 이상 입력 중 같은 양의 간격 80% 이상 반복, 총 300회 이상을 참고 신호로 표시한다. 이는 시간 정밀도·다중 터치에서도 발생할 수 있으며 부정행위 확정 기준이 아니다. 신호만으로 F·점수·순위를 막지 않는다. 기존 기록도 저장된 이벤트로 계산하며 공개 DTO에는 신호/원본 배열을 넣지 않는다.

실제 방어는 서버 발급 도전 일정, 소유권·현재 슬롯·해금, 형식/시각 범위, 입력 상한, 사용자별 요청 제한, 멱등성과 DB 고유 제약이다. 클라이언트 이벤트만으로 매크로를 완벽히 구분할 수 없다. 추가 과제로 서버 난수 기반 상호작용 과제·구간별 접수 등을 검토할 수 있으나 게임 UX/느린 네트워크 영향과 정상 사용자의 오탐을 먼저 검증해야 하며 현재 구현했다고 주장하지 않는다.

## 운영 API

모두 현재 ADMIN·세션/CSRF 검증을 사용한다. 쓰기는 `Idempotency-Key` 16~64자와 명시적 확인·사유가 필요하다.

| API | 요청·동작 |
| --- | --- |
| `GET /api/v1/admin/tap-attempts?filter=FAILED&offset=0&limit=25&q=...` | 실패/전체 현재 도전, 아이디·이름·닉네임 검색. 실제 제출 없이 기한만 지난 슬롯도 EXPIRED로 표시. 다음 페이지와 복구/재도전 가능 여부 제공 |
| `POST /api/v1/admin/tap-attempts/members/{id}/restore` | `{attemptId,expectedGeneration,reason,confirmation:"RESTORE"}` → `{attemptId,userId,recognizedAt,restoredAt}` |
| `POST /api/v1/admin/tap-attempts/members/{id}/retry` | `{attemptId,expectedGeneration,reason,confirmation:"RETRY"}` → 기존 미션 조정 이력 |

조회는 한 페이지와 그 도전의 입력만 묶어 읽는다. 전체 이벤트를 브라우저로 보내지 않으며 지원 상태를 Redis에 캐시하지 않는다. 정식 시상·무제한 도전·운영 전체 데이터 일괄 변경은 포함하지 않는다.
