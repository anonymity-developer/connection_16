# SYNC ME 퍼널 MVP

격리 worktree의 V23 재번호 후보다. 원본 PR #37은 V21과 1f565dc를 그대로 유지한다. main 병합·운영 배포·운영 DB 검증을 의미하지 않는다. 계약은 [OpenAPI](funnel.openapi.yaml)에 있다.

## 수집과 집계

- `POST /api/v1/sync/funnel-events`: 실제 참가자 설문 화면의 `SCREEN_ENTER`(0), 표시된 `QUESTION_VIEW`(1~실제 API 문항 수, 최대 20). 현재 설문은 9문항이지만 코드에 9를 고정하지 않는다.
- 질문 화면을 성공적으로 불러온 때를 시작으로 정의한다. 잠긴 화면·로딩 실패·미설정 문항·이미 저장된 결과 화면은 시작으로 세지 않는다. 다음/이전 질문 이동을 기록하고 답 선택·일반 재렌더링·StrictMode effect 재실행은 중복 전송하지 않는다. 중간 이탈 후 다시 들어오면 새로운 진입과 첫 질문을 기록한다.
- `GET /api/v1/admin/funnel`, `/admin/funnel`: 현재 문항 버전, 현재 ACTIVE/USER 참가자, 사용자별 현재 reset generation의 고유 사용자 수. 이전 문항 버전과 초기화 이전 이벤트는 보존하되 이 화면에서는 제외한다. 비활성화된 계정과 독립 운영자는 제외한다. 재가입은 새 user ID로 별개다.
- 각 단계의 사용자 집합을 독립 집계한다. 동일 단계 반복 방문·중복 요청·재진입은 한 사람이다. 순서대로 모든 단계를 거친 코호트나 세션별 이탈 확정치가 아니다. 이탈률 = `(직전 단계 인원 - 현재 단계 인원) / 직전 단계 인원 * 100`, 전환율 = `현재 단계 인원 / 화면 진입 인원 * 100`. 분모 0은 null/—, 누락에 따른 음수 이탈률·100% 초과 전환율은 숨기지 않는다.
- `SUBMIT_SUCCESS`는 클라이언트 입력을 받지 않는다. 실제 제출 트랜잭션이 커밋한 기존 `sync_results`를 조회하며 현재 버전이고 `submitted_at >= collectionStartedAt`인 결과만 센다. 저장 재시도는 기존 PK에 따라 한 번만 집계된다. 관리자 수동 글자 지급은 설문 결과가 아니므로 포함되지 않는다. 초기화로 보관된 과거 결과는 제외한다.
- V23 실행의 DB UTC 시각이 `collectionStartedAt`이다. 프론트/서버 활성화까지의 공백, 네트워크 장애·상한 초과로 누락된 이벤트와 도입 이전 조회는 소급할 수 없다. `submitted_at`은 기존 서버 접수 시각이며, 결과 행의 커밋을 확인하는 방식이지 커밋 시각을 새로 기록하는 기능은 아니다.

## 보안과 장애 경계

세션의 내부 user ID만 사용한다. CSRF, ACTIVE/credential version, DB USER 역할, 독립 운영자 제외, 행사 OPEN, 미션 활성/NFC 해금, 프로필·동의 자격, reset-generation 헤더를 검사한다. 관리자 조회는 기존 SecurityConfig의 ADMIN 검증과 같은 집계 트랜잭션 안의 현재 DB 역할 검증을 모두 적용한다.

관리자 미리보기는 기존 memory client를 사용하고 로거를 전달하지 않는다. 직접 사용하는 개발 `SyncMissionView`도 기본적으로 로깅이 없다. 비인증·관리자 요청을 서버에서 거절한다. 정상 참가자가 인증 후 자신의 화면 조회를 조작하는 것을 완벽히 증명하는 장치는 아니며 분석 이벤트를 미션 완료·시상·인가 근거로 사용하지 않는다.

브라우저 요청은 최대 2초, 동시 최대 4건, 화면 마운트당 최대 200회 질문 표시를 전송한다. 자동 재시도·영속 큐·localStorage는 없다. 분석 응답은 기존 인증 오류 이벤트를 발생시키거나 CSRF/세션 상태를 변경하지 않는다. 수집 실패가 제출/질문 이동의 await 경로에 들어가지 않는다.

서버는 사용자별 분당 120회와 누적 최대 2,000행을 적용한다. 사용자 잠금 아래 상한과 `(user_id,event_key)` 중복을 확인한다. 같은 키 재전송은 기존 행을 유지한다. 입력의 문항 버전·단계·유형·길이를 검증하며 발생 시각은 DB 현재 시각 기준 과거 24시간~미래 5분만 허용한다. 통계에는 클라이언트 시각을 필터로 사용하지 않는다. 관리자 조회는 분당 30회다. 수집은 제출과 별도 HTTP 요청/2초 제한 트랜잭션이며, 장애 시 실패 응답을 무시한다. 공유 DB/Redis 자체의 전체 장애까지 사용자 진행을 보장한다는 의미는 아니다.

## 데이터와 마이그레이션

V23은 `funnel_collection` 1행과 `mission_funnel_events`만 추가한다. 기존 테이블·인증·제출·완료 경로·마이그레이션은 변경하지 않는다. 이벤트는 내부 user ID(FK), 미션, 문항 버전, reset generation, 중복 방지 UUID, 유형, 단계, 클라이언트 발생 시각, DB 수신 시각을 저장한다. 답변·선택지·IP·이름·닉네임·외부 ID는 추가 수집하지 않는다. 관리자 DTO는 집계 숫자만 반환하고 개별 이벤트 조회/내보내기를 제공하지 않는다.

자동 삭제나 사용자 FK cascade는 없다. 보관/삭제 기간은 기존 행사 데이터 정책과 함께 운영자가 확정해야 한다. 사용자별 누적 상한은 초기화로 풀리지 않는다. 버전·단계·사용자·세대 집계 인덱스와 사용자/키 UNIQUE가 있다. 실제 운영 규모에서의 부하 검증은 별도다.

## 배포와 롤백

이 작업에서는 배포하지 않는다. 추후 승인된 배포에서 백업 후 Flyway V23을 먼저 적용하는 서버 버전, 그다음 프론트를 배포한다. 수집 시작 시각을 다시 설정하거나 과거 이벤트를 채우지 않는다. 서버가 이전 버전이면 프론트의 이벤트 404는 무해하지만 집계 화면은 오류를 표시한다. 기존 세션·NFC·미션 제출 계약은 동일하다.

롤백은 이전 프론트/서버 이미지로 되돌린다. 새 테이블과 Flyway 이력은 남겨 이전 기록을 보존한다. 적용한 V23 파일 수정, Flyway 이력 삭제, 자동 DROP은 하지 않는다. 테이블 제거는 이후 별도 승인된 마이그레이션과 보관 정책으로 수행한다.

P1의 SHOW ME / A WISH COME TRUE / FAST TAP / YOU GOT THIS 화면 이벤트는 이번 범위에 포함하지 않는다. 기존 관리자 현황·서버 결과는 유지하며, 공통 이벤트 저장 구조를 실제 확장할 때 미션별 정의와 제약을 추가한다.

## 로컬 검증 환경

Java 21과 Docker의 Testcontainers MySQL/Redis를 사용한다. 통합 테스트가 덮어쓰는 JDBC URL에는 운영 URL의 `connectionTimeZone=UTC` 옵션이 없으므로, Windows KST JVM에서는 기존 시각 비교 테스트와 새 발생 시각 검증에 9시간 차이가 생긴다. 운영 컨테이너·CI와 같은 UTC JVM으로 실행한다. 예: PowerShell에서 `$env:JAVA_TOOL_OPTIONS='-Duser.timezone=UTC'` 후 `backend/gradlew.bat -p backend test integrationTest bootJar`. 이 설정은 해당 프로세스에만 적용하며 테스트 기대값·인가 조건을 완화하지 않는다.

화면은 사용자 승인에 따라 기존 관리자 틀·DM Sans를 유지한 achromatic-ledger 방향이다. 단계별 숫자 표로 “어느 질문에서 참여 인원이 줄었는가”를 먼저 보여준다. 시각 검사에서 관리자 전체 높이 틀의 빈 공간 경고는 기존 공통 레이아웃을 보존하기 위해 허용하며, 새 표의 숫자는 모바일에서도 오른쪽 정렬한다. 브라우저 검사의 합성 데이터는 테스트 스크립트에만 있고 제품에는 하드코딩하지 않는다.

- 기존 UTC 실행 증거를 재사용했다. Java 21 Gradle 로그의 `JAVA_TOOL_OPTIONS: -Duser.timezone=UTC`, 11:53 KST의 `BUILD SUCCESSFUL`, JUnit XML과 생성 JAR을 대조했다. 백엔드 단위 99개 통과, 전체 통합 209개 중 208개 통과·실패 0개·건너뜀 1개, `bootJar` 성공이다. 건너뛴 항목은 `TAGME_REHEARSAL_FAULTS=1`에서만 실행하는 선택형 의존성 중단/복구 검사이며 통과로 세지 않는다.
