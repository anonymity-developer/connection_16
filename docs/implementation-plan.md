# 상세 구현 계획

## 1. 현재 상태와 개발 순서

이 문서는 구현할 작업의 계약이다. 초기 구성 외 기능을 완료한 것으로 간주하지 않는다. 각 단계는 아래 완료 기준을 만족한 뒤 체크한다.

| 단계 | 작업 | 완료 기준 | 현재 상태 |
| --- | --- | --- | --- |
| 0 | 모노레포, ignore, 빌드, Docker, CI, 핵심 마이그레이션 | 양쪽 빌드, DB/Redis 연결, API 프록시, 시드 확인 | 빌드/단위/Compose 설정 검사 통과; 실제 컨테이너 구동은 미검증 |
| 0.5 | 모바일 UI 방향, 디자인 토큰, 공통 컴포넌트, 핵심 화면 | 인증/홈 수집판/대표 미션/글자 획득 화면과 상태별 표현 확인 | 예정; 기능 연결보다 먼저 진행 |
| 1 | Mattermost 사전 검증, OTP, 세션 | 지정 채널 참여자만 로그인, 재사용/과다 시도 차단 | 예정 |
| 2 | 프로필, 태그, 수집판, 공통 완료 | 최초 프로필 완료, 해금/완료 멱등성, 5개 판정 | 예정 |
| 3 | SYNC, 소원/응원 및 검수 | 1인 1슬롯, 결과 1회, 승인된 콘텐츠만 게시 | 예정 |
| 4 | FAST TAP | 1회 공식 슬롯, 중복 시작/종료 대응, 모바일 검증 | 예정 |
| 5 | 탐색/추천, 방문, 그래프 | 비공개 필터, 중복 간선 없음, 상호 방문 반영 | 예정 |
| 6 | 관리자, 시상 정산, 배포 검증 | 검수/신고/재도전/수상 확정과 감사 이력 | 예정 |

### 1.1. UI 품질 기준

UI 품질은 행사 필수 범위다. 공통 디자인을 먼저 정하고 인증 → 수집판 → 대표 미션 → 글자 획득의 모바일 화면을 구성한 뒤 API를 연결한다. 이후 각 미션으로 확장하며, 복잡한 효과를 제외한 기본 디자인과 상호작용은 초기 범위에 포함한다.

| 대상 | 구현 및 확인 기준 |
| --- | --- |
| 공통 디자인 | 색상/타이포/여백/둥근 모서리/그림자를 토큰으로 관리하고 버튼, 입력, 카드, 상태 배지를 공통 컴포넌트로 사용 |
| 인증 | 숫자 6자리, 앞자리 0 유지, 숫자 키패드, 전체 코드 붙여넣기, 만료/오답/재발송 대기/전송 오류 표시 |
| 홈 수집판 | 다섯 칸과 서로 다른 두 S 미션 식별, 현재 진행도 및 다음 행동 표시, 잠김/해금/검수 대기/완료 구분 |
| 개별 미션 | 소원 호수/응원 카드/성향 결과/탭 영역의 개성을 유지하고 공통 내비게이션과 버튼 규칙 적용 |
| 피드백 | 글자 획득과 전체 완성 모션, 중복 제출 방지, reduced-motion 대체 표현, 서버 확정 상태에 맞는 문구 |
| 화면 상태 | 정상/로딩/빈 목록/오류/미해금/검수 대기를 같은 디자인 수준으로 구성하고 복구 행동 제공 |
| 모바일 | 360/390/430 CSS px에서 가로 넘침 없음, 주요 터치 영역 최소 44×44 CSS px, 키보드와 safe area에 주요 버튼이 가려지지 않음 |

아이콘이나 색상만으로 상태를 구별하지 않고 텍스트를 함께 제공한다. 입력 레이블과 키보드 포커스를 유지한다. iOS Safari와 Android Chrome의 실제 기기에서 인증 입력, 스크롤, 탭 연타, 뒤로가기를 확인한다. 핵심 흐름의 화면 검증을 각 기능의 완료 기준에 포함한다.

## 2. 첫 기술 검증

1. 운영에 사용할 권한으로 Mattermost 사용자 조회, 지정 채널 멤버십 조회, DM 생성/발송을 각각 확인한다. 교육생 개인정보 없이 결과와 필요한 권한만 기록한다.
2. iOS Safari / Android Chrome에서 NFC URL 진입, QR 대체 진입, 로그인 후 원래 태그 복귀를 실제 기기로 확인한다.
3. 탭 영역에서 연타 시 페이지 이동/확대/스크롤이 발생하는지, background 전환과 화면 잠금이 어떻게 전달되는지 확인한다.
4. 검수 제공자의 한국어 응답 품질, 개인정보 감지 지원, 응답 시간, 오류 정책을 측정한다. provider-neutral adapter 뒤에 연결하고 특정 API가 모든 정책을 지원한다고 가정하지 않는다.
5. Docker가 가능한 환경에서 통합 테스트와 전체 스택 smoke를 실행한다. 이 환경의 성공이 실제 행사 용량 보장을 의미하지는 않는다.

Mattermost 권한을 얻지 못하면 가짜 OTP/고정 인증번호를 운영에 넣지 않는다. 인증 방식 변경을 결정한 후 해당 단계의 계약을 갱신한다.

## 3. 인증 구현

### 요청 흐름

`CSRF 발급 → 사용자 조회 → 채널 멤버십 검증 → OTP 생성/DM 전송 → OTP 검증 → 회원 upsert → 세션 생성`

- 인증번호는 **숫자로만 구성된 정확히 6자리 문자열**이다. `000000`부터 `999999` 범위에서 암호학적으로 안전한 난수 생성기로 발급하고 앞자리 0을 유지한다. 영문/기호 혼합 코드를 사용하지 않으며 발급할 때마다 새로 생성한다. 고정 공용 번호를 계정 인증에 사용하지 않는다.
- 제안 기본값은 TTL 3분, 계정당 발송 간격 60초, challenge당 검증 5회다. IP와 계정 두 축으로 제한하고 운영 설정으로 조절한다.
- 요청 DTO의 `code`는 숫자 타입이 아닌 문자열이며 서버에서 `^[0-9]{6}$`로 검증한다. 입력은 `type="text"`, `inputMode="numeric"`, `autoComplete="one-time-code"`, `maxLength={6}`를 기본으로 하고 붙여넣기와 앞자리 0을 보존한다. OTP 원문은 URL에 넣지 않는다.
- OTP 원문 대신 서버 비밀키를 이용한 HMAC과 무작위 challenge ID를 Redis에 보관한다. 비밀키는 운영 환경변수로 추가한다. 비교/시도 횟수 증가/성공 시 소진은 원자적으로 처리한다.
- 사용자 존재/멤버 여부가 드러나지 않는 공통 요청 응답을 사용한다. DM 발송 실패는 challenge를 성공 상태로 남기지 않는다.
- 재발송 시 이전 challenge 무효화 정책을 고정한다. 성공한 OTP는 재사용할 수 없다.
- 검증 시 멤버십을 다시 확인하고 서버에서 조회한 `mattermost_id`로 회원을 찾는다. 표시 이름은 정보 추출 보조값이며 변경되지 않는 계정 키가 아니다.
- 최초 로그인 시 필수 개인정보 확인/동의를 거친다. 최초 계정에는 USER만 부여한다. ADMIN 승격은 별도 운영 절차로 처리한다.
- Spring Security의 인증 성공 흐름에서 세션 ID를 바꾸고 SecurityContext를 저장한다. 로그아웃은 세션 무효화 후 CSRF 재발급으로 이어진다.

검증: 앞자리 0 유지, 6자리 붙여넣기, 길이 오류/영문/기호 거부, 만료, 오답 5회, 동시 검증, 재사용, 재발송, 채널 탈퇴, DM 장애, 세션 ID 교체, 로그아웃 후 접근 차단.

## 4. 프로필 및 태그

- 프로필 필수값은 닉네임, 한 줄 소개, 관심사와 공개 동의를 기본안으로 한다. 실명/지역/반은 인증 정보 확인 절차와 연결한다.
- 길이, HTTPS URL, 관심사 ID 존재 여부를 서버에서 검증한다. 초기에는 외부 이미지 업로드를 구현하지 않고 이미지 사용 권한을 검증한 URL 또는 기본 아바타로 시작한다.
- 목록 DTO와 상세 DTO를 구분한다. 목록의 JSON에도 실명/반/Mattermost ID를 넣지 않는다.
- 메인 주소는 공개 진입점이고 실제 참여에는 인증이 필요하다. 태그 URL만 `/t/{token}` 형태로 만들며 일반 화면/API 이름은 읽기 쉽게 유지한다. 미션 코드, 글자, 순번을 태그 토큰으로 사용하지 않는다.
- 태그별로 암호학적으로 안전한 무작위 바이트 32개를 생성하고 padding 없는 Base64URL로 인코딩한다. 토큰은 43자리이며 허용 형식은 `^[A-Za-z0-9_-]{43}$`다. 이는 사용자가 입력하는 숫자 6자리 OTP와 별개의 값이다.
- 로그인 후 `POST /api/v1/tags/resolve`에 토큰을 보내 처리한다. GET만으로 해금하지 않는다. 인증 전 태그 진입 정보를 같은 탭의 임시 상태로 보존하고 인증 후 해당 태그로 복귀한다. 복귀 경로는 내부 허용 경로만 사용하고 외부 URL로 리다이렉트하지 않는다.
- 토큰의 SHA-256만 DB에 저장한다. 여러 NFC/QR을 동일 미션에 연결할 수 있으며 태그 비활성화/교체를 지원한다. 원문 토큰은 운영 배포물로 별도 관리하고 저장소, 공개 API 목록, 분석 이벤트, 요청 로그에 노출하지 않는다. 태그 진입 페이지는 외부 요청에 토큰 URL이 전달되지 않도록 Referrer-Policy를 적용한다.
- 서버는 세션, 토큰 형식/해시 일치, 태그/미션 활성 여부, 행사 기간을 확인한 뒤 해금한다. 해금 이후에도 각 미션 수행 API에서 해당 사용자의 해금 기록을 다시 확인한다. 프론트 잠금이나 URL 은닉을 권한 검사로 대신하지 않는다.
- 미해금 상태는 `mission_progress` 행 없음으로 표현한다. 첫 해금 시 행을 삽입하고 중복 해금은 현재 상태를 반환한다.
- 프로필을 먼저 완성했더라도 SHOW ME 태그가 해금되지 않았다면 완료하지 않는다. 해금 시 기존 유효 프로필을 재평가한다.
- 태그 URL을 공유하면 다른 사람도 해금할 수 있다. 초기 설계의 NFC/QR은 미션 진입 장치이며 현장 체류를 증명하는 장치가 아니다.

검증: 태그 비활성/잘못된 토큰, 코드나 순번으로 해금 시도, 미인증 resolve, 미해금 상태에서 화면 URL/API 직접 접근, 동시 해금, 인증 전 진입 복원, 외부 복귀 URL 차단, 완료 후 재접속, 비공개 상세 요청, 목록/로그/Referer의 토큰 누출.

## 5. 완료 트랜잭션과 순번

모든 미션은 `MissionCompletionService.complete(userId, missionCode, evidence)`를 통해 완료한다. 컨트롤러에서 완료 시각을 받지 않는다.

```text
BEGIN
1. users 해당 행 SELECT ... FOR UPDATE (사용자별 직렬화)
2. 행사 기간, 계정 상태, 미션 활성/해금 상태, 결과 근거 확인
3. 이미 완료면 저장된 결과 반환
4. 최초 완료만 UPDATE; completed_at을 덮어쓰지 않음
5. 필수 5개 mission code가 모두 완료인지 확인
6. event_completions가 없을 때만 sequence id=1 FOR UPDATE
7. next_value로 완료 순번 INSERT + next_value 증가
COMMIT
```

여러 미션이 한 사용자에게 동시에 완료되어도 마지막 판정이 누락되지 않도록 사용자 행 잠금을 **쓰기 전에** 얻는다. 잠금 순서는 사용자 → 콘텐츠/미션 → 전역 sequence로 통일한다. 전역 sequence 잠금 안에서는 외부 호출을 수행하지 않는다. 교착 재시도는 멱등한 단위로 제한하고 DB 예외를 일반 성공으로 숨기지 않는다.

`completion_order`는 **승인 처리까지 끝난 운영상 완료 순번**이다. 이를 검수 지연을 보정한 선착순 수상 순위라고 노출하지 않는다. 최종 시상은 아래 정산 단계에서 별도로 계산한다.

검증: 동일 완료 20개 병렬 요청, 같은 사용자의 다른 마지막 미션 동시 완료, 여러 사용자의 최종 완료, sequence 증가 직후 롤백. 기록 1개, 순번 유일성, 롤백 시 증가 취소를 실제 MySQL에서 확인한다.

## 6. 소원/응원과 비동기 검수

### 저장 모델

사용자별 소원/응원 슬롯을 UNIQUE로 확보한다. 콘텐츠 원본 슬롯, 변경 불가능한 revision, 검수 작업을 구분한다. `approved_revision_id`는 공개 중인 버전, `pending_revision_id`는 검수 중인 버전이다. 새 수정안이 거절되어도 기존 승인본은 유지한다. 운영자가 숨기면 슬롯 상태를 HIDDEN으로 바꿔 모든 버전을 비노출한다.

### 제출

1. 인증/CSRF/해금/행사 기간/입력 길이/속도 제한을 검증한다.
2. 한 트랜잭션으로 슬롯 생성 또는 수정, revision 생성, 검수 작업 생성, 서버 접수 시각을 저장한다.
3. `202 Accepted`와 콘텐츠 ID/검수 상태를 반환한다. 미션은 아직 완료하지 않는다.
4. 작업자가 DB에서 미처리 작업을 lease로 claim하고 트랜잭션을 끝낸 뒤 외부 API를 호출한다.
5. 결과를 반영할 때 revision 및 작업 버전, pending 포인터를 확인한다. 이전 버전 응답이 최신 수정을 덮어쓸 수 없다.
6. 승인되면 공개 포인터를 전환하고 최초 승인일 때만 미션을 완료한다. 재처리도 같은 결과를 만든다.

작업 상태는 `QUEUED → PROCESSING → APPROVED / REJECTED / REVIEW_REQUIRED`다. 일시적 오류는 지수 백오프로 제한 횟수 재시도하고, lease 만료 작업은 회수한다. 장애 또는 판정 불확실은 관리자 검토로 보낸다. 별도 메시지 브로커 없이도 DB에 작업을 남겨 프로세스 중단 후 복구한다.

### 정책

길이/URL/반복 제출은 규칙으로 검사하고, 모욕/혐오/괴롭힘 등은 선택한 검수 API 및 운영 규칙으로 판정한다. 전화번호 등 개인정보 감지는 별도 규칙을 함께 적용한다. 외부 API에는 콘텐츠 텍스트만 보낸다. 이름, 계정 ID, 지역/반은 보내지 않는다.

댓글도 승인 후 공개하고, 거절/보류 댓글은 작성자와 관리자에게만 상태를 보여준다. 운영자의 승인/거절/숨김 조치는 사유와 변경 전후 상태를 감사 로그에 남긴다.

검증: 동시 최초 작성, 제출 직후 재시작, 같은 작업 중복 처리, 처리 중 수정, 이전 응답의 지연 도착, API timeout, 승인 후 숨김, 거절 후 재작성. 무검수 콘텐츠가 공개되지 않아야 한다.

## 7. FAST TAP

- `tap_slots.user_id`를 PK로 공식 슬롯 하나를 보장한다. 실제 도전은 `tap_attempts`에 남기고 슬롯이 현재 attempt를 참조한다. 재도전은 관리자 승인으로 새 attempt를 만들며 이전 이력은 지우지 않는다.
- 시작 요청은 idempotency key로 중복을 구분한다. 서버가 `attemptId`, `startsAt=서버 현재+5초`, `endsAt=startsAt+10초`, 제출 허용 종료 시각을 발급한다.
- 카운트다운 취소는 서버 현재 시각이 startsAt보다 이른 경우에만 허용한다. 시작 이후의 이탈/취소는 기회가 소진된다.
- 클라이언트는 단조 증가 타이머로 연출하고 `pointerdown` 이벤트, 상대 시간, visibility 변경을 기록한다. 점수 영역의 CSS에 `touch-action: none`, `user-select: none`을 적용한다.
- 점수는 서버가 검증된 이벤트 개수에서 계산한다. 시작/종료 창, 이벤트 순서, 개수 일치, 제출 유예, 비정상 간격을 확인한다. 유예는 전송 지연용이며 플레이 시간 연장이 아니다.
- 종료 중복 제출은 최초 확정 결과를 반환한다. 다른 payload로 재제출하면 409로 응답한다. 네트워크 재연결 시 `/tap/me`에서 서버 상태를 복구한다.
- 상태는 `COUNTDOWN → PLAYING → SUBMITTED → VALID / REVIEW_REQUIRED / INVALID`다. 시작 이전 취소와 시작 이후 중단을 구분한다. 시간 경과 상태는 서버 타임스탬프로 계산한다.
- 웹 이벤트 자체의 조작 가능성은 남는다. 순위에는 잠정 여부를 표시하고 수상 후보는 관리자가 최종 검증한다. 의심 기록은 임의로 정상 판정하지 않는다.

완료 인정은 VALID 결과를 기본으로 한다. 보류 결과의 미션 완료/시상 처리는 검토 결과에 따라 확정한다. 실제 브라우저 장애 재도전은 attempt 이력, 관리자 사유, 승인자를 함께 기록한다.

## 8. SYNC 및 동료 탐색

SYNC는 문항 ID/선택지 유효성을 서버에서 확인하고 버전별 점수표로 계산한다. 축 점수가 같을 때의 우선순위도 고정한다. `(user_id)` PK로 재제출 시 기존 결과를 반환하며, 다른 답변으로 결과를 바꾸지 않는다.

추천 초기안은 공통 관심사 비율, 성향 유사도, 공통 활동을 각각 정규화해 가중 합산한다. 가중치는 설정으로 분리하고 노출 이유를 함께 반환한다. 자신/비공개/차단 계정을 먼저 제외한다. 신규 사용자에게는 공통 관심사와 아직 방문하지 않은 동료를 중심으로 fallback을 제공한다. 성과를 확인하기 전 가중치가 효과적이라고 단정하지 않는다.

프로필 방문은 조회자 행을 잠그고 공개 상태를 확인한 뒤 `(viewer_id, viewed_id)`를 최초 1회만 삽입한다. 프로필 숨김도 같은 사용자 행 잠금 규칙을 사용해 쓰기 순서를 맞춘다. 추천/그래프 응답은 항상 현재 공개 상태를 다시 필터링한다. 본인 프로필 방문으로 간선을 만들지 않는다.

초기에는 프로필 응답을 공유 캐시하지 않는다. 통계를 포함한 사용자별 응답은 `Cache-Control: no-store`를 적용한다. 첫 방문/반대 방문 유무를 바탕으로 단방향 및 상호 발견을 표시한다. 커서 페이지네이션과 최대 그래프 노드 수를 적용해 전체 사용자 데이터를 무제한 반환하지 않는다.

## 9. 최종 시상 정산

검수 처리 시간이 선착순을 바꾸지 않도록 **미션별 유효 근거의 최초 서버 접수 시각**을 별도 저장한다. 초기 스키마의 `completed_at`만으로는 이를 복원할 수 없으므로 콘텐츠 기능 단계에서 `mission_completion_evidence` 및 원본 revision 참조를 추가한다.

1. 제출 마감 시각 이전의 후보를 고정한다. 검수 대기 건은 사전 공지한 정산 마감까지 처리한다.
2. 각 미션의 승인된 유효 근거 중 최초 접수 시각을 구한다. 수정안이 처음으로 유효했다면 그 수정안의 접수 시각을 사용한다.
3. 사용자별 다섯 근거의 최댓값을 유효 전체 완성 시각으로 계산한다.
4. 전체 완성상은 유효 전체 완성 시각 → 최초 서버 접수 순서의 고유 ID → user_id 순으로 정렬한다. 동점 우선순위는 운영 공지와 일치시킨다.
5. 댓글 활동상은 타인의 유효한 소원에 남긴 승인 댓글의 `COUNT(DISTINCT wish_id)`로 집계한다. 반복 댓글/자기 댓글/숨김 콘텐츠는 제외한다.
6. 응원 반응상은 유효 카드의 서로 다른 사용자 하트로 계산한다. 자신의 카드 하트는 허용하지 않는다.
7. 게임상은 유효 공식 attempt만 정렬하고 동점 기준을 공지한다. 재도전 승인 전 기록과 중단 기록은 후보에서 제외한다.
8. 관리자 검토 후 후보, 근거, 정산 시각, 알고리즘 버전을 snapshot으로 저장하고 수상을 확정한다.

그 후의 콘텐츠 숨김이나 탈퇴가 이미 발표한 순위를 자동으로 재정렬하지 않게 한다. 정정은 별도 운영 조치와 이력을 남긴다. 랜덤상은 고정한 적격 집합과 추첨 결과를 보관한다. 시상 종류와 인원은 아직 확정하지 않았다.

## 10. 운영 및 검증 완료 기준

- 관리자: 회원 제한, 검수 보류 처리, 콘텐츠 숨김/신고, 게임 재도전, 시상 확정, 이벤트 마감 설정과 감사 로그.
- MySQL 통합 테스트: 1회 제약, 동일 사용자 동시 완료, 순번 롤백, 검수 버전 경합, 중복 하트/방문.
- API 보안 테스트: 세션 없음, CSRF 없음, 타인 수정, 해금 전 접근, 익명 작성자 ID 누출, 비공개 프로필 누출.
- E2E: OTP → 태그 복귀 → 5개 미션 → 완성 → 동료 상세 → 상호 발견 → 관리자 정산.
- 실기기: iOS/Android의 NFC, 터치, 탭 중단, 새로고침/뒤로가기, 좁은 화면의 그래프.
- UI: 1.1의 화면별 기준, 숫자 키패드/붙여넣기, 360/390/430 CSS px 화면, 키보드/safe area, 상태별 안내와 모션 감소 설정을 확인한다. 기능 정상 동작만으로 UI 검증을 완료 처리하지 않는다.
- 부하 테스트: 총 가입자 2,000명과 동시 접속자 수를 구분해 시나리오를 만든다. 예상 동시 요청부터 단계적으로 늘리며 p95/오류율/DB 잠금/자원 사용을 기록한다. 목표치는 행사 조건을 정한 뒤 확정한다.
- 운영: 백업을 새 DB에 복원하고 마이그레이션/헬스체크를 확인한다. Redis 장애 시 인증/세션 요청을 정상 성공으로 처리하지 않는다.
