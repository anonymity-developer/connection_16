## P1 화면과 원본 브랜치의 기존 검증

[화면 구성](all-page-events-ui-proposal.md)의 네 탭은 이벤트 로그·페이지 방문·이동 흐름·미션 퍼널이다. KST 종료일 포함 최대 31일을 UTC `[from,to)`로 바꾸고 오늘은 조회 시점까지 고정한다. 원시 로그에만 페이지/유형 필터와 50행 서버 페이지네이션을 적용한다. 일별 미관측은 수집 전 `—`와 수집 후 `0`을 구분하며, 퍼널은 서버 비율을 그대로 표시하고 SYNC 문항별 상세는 기존 `/admin/funnel`로 연결한다. ADMIN 확인 전에는 조회하지 않으며 401/403은 분석 화면을 제거한다. 새 쓰기 API·내보내기·마이그레이션은 추가하지 않는다.

2026-11-17 검토에서 프론트 lint·단위 120개·운영 빌드·`test:page-events-ui`·`test:admin-ui`를 재실행해 통과했다. 페이지 이동·필터·고정 시각·잘못된 기간·늦은 응답·로딩/빈 데이터/오류/재시도·권한 회수와 네 탭의 360/390/430/768/1440px를 검사하고 스크린샷을 확인했다. P1 소스 및 로그/방문 렌더 검사기는 FAIL/WARN 0개다. 검사 스크립트의 중복 FAIL 판정은 리포트의 실제 `level` 필드로 보정했다(기존 inspector 종료 코드 검사도 유지). 기존 SYNC 화면의 공통 시트 하단 여백 WARN 1개는 P1 기능 실패와 구분한다. 기존 Framed sheet 방향(seed `215396526`)과 TAG ME 관리자 셸을 유지했으며 새 방향을 뽑거나 스타일을 다시 만들지 않았다. 표의 원시 근거가 화면의 주 질문을 답하고, 방문 합계는 행에서 계산하며, 모바일은 표를 라벨 있는 행으로 전환한다. 검사 전용 합성 데이터는 브라우저 응답에만 있고 빌드/실제 DB에 넣지 않는다.

진행 중으로 보고됐던 최종 V23 백엔드 전체 실행은 16:19 KST에 완료됐다. Gradle 완료 로그와 JUnit XML 기준 단위 100개 통과, 통합 총 224개 중 223개 통과·선택형 장애 주입 1개 건너뜀·실패/오류 0개, bootJar 성공이다. 이 통합 실행은 분석 14개와 기존 V21 데이터 보존·구 writer 호환성을 검사하는 V23 업그레이드 1개를 포함한다. 이번 검토에서 백엔드 코드는 변경하거나 수트를 중복 실행하지 않았다. 실제 운영 데이터/DB와 main TAP 복구 경로의 통합 검증으로 확대하지 않는다.

## 이벤트와 중복 방지

- `PAGE_VIEW`: 실제 라우트·동일 경로 이동·뒤로/앞으로·새로고침·하위 화면/대화상자 재진입을 관측한다. 렌더 변경만으로 새 방문을 만들지 않는다. BFCache 복원도 새 방문이다.
- `MISSION_STEP_VIEW`: DOM에 표시되고 뷰포트에 들어온 허용 단계만 관측한다. 숨긴 문항/닫힌 대화상자는 제외한다. SYNC의 질문은 기존 V23 경로에만 저장한다.
- `MISSION_SUBMIT_SUCCESS`: 클라이언트 API가 받지 않는다. 실제 기존 미션 완료 트랜잭션의 AFTER_COMMIT 통지에서 PROFILE/SYNC_RESULT/WISH_REVISION/GAME_ATTEMPT/CHEER_REVISION 근거만 별도 작업자·트랜잭션으로 저장한다. 관리자 수동 지급은 제외한다. 같은 receipt 재처리는 한 행이다. 수정 저장·결과 재열람을 새 최초 완료로 표시하지 않는다.

UUID는 방문/단계별로 한 번 생성하고 USER+CLIENT+UUID UNIQUE로 멱등성을 보장한다. 같은 키로 다른 payload/세션을 보내면 409다. SERVER receipt 키는 별도 namespace여서 클라이언트가 선점하지 못한다. 순수 React 재렌더/StrictMode의 effect 재설정은 같은 관측을 반복하지 않는다.

수집 요청은 기존 `postTelemetry`의 최대 동시 4개·2초 timeout·무재시도·비영속 메모리 경로다. 401/403도 로그아웃/CSRF 초기화/미션 오류를 발생시키지 않는다. 문서당 전송 상한 4,000개다. 서버는 사용자 240회/분, 전체 10,000회/분(기존 SYNC 수집과 공유), USER당 CLIENT 10,000행·SERVER 500행, 새 저장소 누적 1,000,000행 상한이다. V23은 기존 120회/분·2,000행/사용자 제한도 유지한다.

완료 작업자는 1개 스레드·대기 256개이며 포화·장애를 미션 응답으로 전파하지 않는다. 프로세스 종료/재시작/장애 시 누락 가능하며 outbox/재전송 보장은 없다. 해당 프로세스의 완료 기록 실패 카운터를 조회할 수 있지만 재시작하면 초기화된다. **저장 성공 로그 부재가 미션 저장 실패를 의미하지 않는다.**

## 저장 정보와 시각

V24는 `page_events`, 단일 `page_event_collection`과 V23 테이블의 nullable `analytics_session_key`만 additive로 추가한다. V23 파일과 기존 업무 테이블 DDL은 바꾸지 않는다. 세션 값은 기존 서버 HMAC 키로 USER+현재 인증 세션 ID를 digest한 값이다. 세션 자격 증명으로 사용할 수 없으며 관리자는 앞 16자리만 받는다. 이전 V23 행은 세션 미상 그대로 표시한다.

새 로그는 내부 USER FK, 세션 digest, UUID/직전 페이지 UUID, 허용 화면·유형·미션·단계, CLIENT/SERVER 출처, 발생·기록 DB UTC 시각만 저장한다. 토큰·IP·답변·외부 ID·자유 URL·검색어를 저장하지 않는다. CLIENT 시각은 서버 수신 시각이다. SERVER 발생 시각은 실제 미션 완료 DB 시각, 기록 시각은 별도 저장 시각이다. V23은 신뢰 가능한 `received_at`을 사용하고 클라이언트 `occurred_at`을 완료/순서의 근거로 쓰지 않는다.

## 관리자 조회 계약

`GET /api/v1/admin/events`는 `[from,to)` UTC 기간(최대 31일), screen/type 허용 필터, offset(0–100000)/limit(1–50)를 받는다. 최신 기록 시각·출처·PK 역순과 전체 수/다음 offset을 반환한다. 같은 조회의 종료 시각을 고정하되 offset 방식이므로 이후 비활성화 등 cohort 변경 시 페이지 구성은 달라질 수 있다. 운영자 역할·세션 버전은 DB에서 재검증한다. 참가자·익명은 403/401이며 두 조회 API 모두 ADMIN 전용이다.

원시 행은 발생/기록 시각, 화면 ID/이름, 유형, 미션·단계, `P-내부ID`, 세션 접두사, 출처만 제공한다. 신원 검색/내보내기는 제공하지 않는다. V23 질문을 UNION으로 조회하므로 복사·중복 저장 없이 실제 기존 기록을 볼 수 있다.

`GET /api/v1/admin/events/summary`는 동일 기간에서 다음을 계산한다.

- PAGE_VIEW 총수, 페이지별 고유 USER, 같은 페이지를 기간 내 2회 이상 관측한 고유 USER. 재방문은 기간 밖 이전 방문을 추정하지 않는다.
- KST 일자별 방문수·고유 USER. 기록 없는 날은 응답 행이 없다.
- USER·세션이 같고 정확한 직전 UUID가 저장되어 있는 이동 상위 20개. 빠진 이벤트를 건너뛰지 않고 탭 간 시각순 기록을 임의로 연결하지 않는다. 새로고침·새 문서의 연결은 끊긴다. 목적지의 기록 시각으로 기간을 제한해 직전 페이지는 기간 밖일 수 있다.
- 다섯 미션의 단계별 고유 USER, 진입 대비/직전 단계 대비 비율, `100-직전 전환율`인 이탈 추정. 분모 0은 null이다. 연습 TAP은 공식 단계에 합치지 않는다. SYNC 질문 상세는 기존 `/admin/funnel`이 담당한다.

현재 ACTIVE USER·credential 보유·비운영자만 원시/집계에 포함한다. 비활성화/역할 변경은 과거 기간의 표시 인원에도 영향을 준다. 새 로그는 초기화 전 실제 관측을 삭제하지 않으며 모든 회차/문항 버전의 기간 내 관측을 포함한다. 단계는 **독립 집계**라 동일 회차의 시간순 코호트가 아니고, 중간 누락/재방문/과거 시작으로 후행 단계가 더 클 수 있다. 단계를 합산해 고유 인원을 만들지 않는다. 기존 `/admin/funnel`의 현재 문항 버전·현재 generation 기준과 의미가 다르다.

마지막 관측은 실제 이탈·포기·대화·추천 클릭을 확정하지 않는다. 클라이언트 관측은 본인 세션·허용 enum·해금 단계까지 검증하지만 인간이 실제 화면을 보았다는 암호학적 증명이 아니다. 미션 완료/해금/시상 권한에는 사용하지 않는다.

## 운영 경계·보관·롤백

기존 운영 정책의 정식 보관 기한은 [운영 문서](operations.md)상 미확정이다. 원시 로그 **30일 보관 후 삭제**를 제안하지만 정책·고지·백업/복원·법적 보존 검토와 별도 승인 전에는 자동 삭제를 구현하거나 활성화하지 않는다. 기존 SYNC/업무 기록도 지우지 않는다. 상한 도달은 수집 누락으로 이어지므로 배포 전에 규모·상한·보관 운영을 결정해야 한다.

페이지/완료 수집은 V24 실행의 UTC `started_at` 이후만 가능하다. 기존 SYNC 질문만 V23 시작 이후 실제 저장분을 볼 수 있으며 과거 페이지를 소급 생성하지 않는다. worker 누락은 재구성하거나 추정 로그로 채우지 않는다.

병합 시 #37 → 이 브랜치 순서가 필요하다. #39는 main 기반 독립 PR이다. 관리자 nav/render와 docs/progress/api/README의 같은 위치를 바꾸므로 후속 병합에서 두 메뉴와 문서를 함께 보존해야 한다. 이 작업에서 #39를 merge/cherry-pick하거나 수정하지 않는다.

**격리 통합 후보(2026-11-18):** main의 V21 TAP 복구 증거와 V22 시스템 복구는 원본 그대로 유지한다. #37 퍼널 SQL은 V23, P0 페이지 SQL은 V24 후보로 파일명만 조정한다. 이 번호와 코드 충돌 해결은 별도 격리 worktree에서만 검증하며 실제 #37/P0 브랜치에는 적용하지 않는다. 기존 P0 검증의 퍼널 V21→페이지 V23 경로와 이번 V20→V21→V22→V23→V24 경로는 별도 결과다. 로컬 유지 fixture DB의 V20 상태는 이전 읽기 전용 조사로 확인했으나 외부 유지 DB의 기존 퍼널 V21/페이지 V23 적용 여부는 미확인이다. 실제 재번호·Push·병합·배포에는 별도 승인이 필요하며 기존 Flyway 이력/checksum을 수정하지 않는다.

배포는 별도 사용자 승인 대상이다. V24 적용 서버를 먼저 준비하고 프론트를 이어야 한다. 구 서버로 앱을 롤백해도 V23/V24 checksum/테이블/기존 기록을 제거하거나 Flyway 이력을 되돌리지 않는다. additive 테이블·nullable 열은 남겨 이전 #37 앱과 호환한다. 신규 frontend가 먼저면 수집 실패/분석 조회 불가가 생기지만 참가자 미션과 격리된다. HMAC 키 회전/세션 교체는 새 세션 그룹으로 보인다. 실제 운영 DB·실기기·현장 부하는 로컬 검증의 범위가 아니다.
